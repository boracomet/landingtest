HeadlessGo

Headless CMS: content types, content manager, REST and GraphQL delivery API, webhooks and preview.

HeadlessGo is a native (compiled-in) Pursae plugin that turns the site into a headless CMS: a Content-Type Builder, a Content Manager and a delivery API for front-end apps (Next.js, Nuxt, Astro, mobile apps…). Its model and query language follow the conventions of the popular open-source headless CMSs (collection types, single types, components, dynamic zones, filters[field][$op], populate, documentId), so front-end code written for them needs few changes. Like every native plugin it is off on a fresh install (native_headlessgo); while it is off its routes answer 404, its menu is gone and the front end renders as usual. Schemas, entries, tokens and webhooks stay in the database when it is deactivated.

Legend: ✓ implemented · ≈ implemented differently (reason given) · ✗ left out (reason given).

1. Storage

  • Schemas (types and components) are JSON documents in hg_schemas (migration 0020_headlessgo.sql). The registry is cached per server and dropped on every schema write.
  • Entries of every type live in one table, hg_entries: one row per document and locale, with data (the draft: the latest saved values) and published_data (the published snapshot, NULL while unpublished) as JSONB, plus typed columns document_id, type_uid, locale, published_at, created_at, updated_at, created_by, updated_by. GIN indexes on both JSONB columns serve the unique checks and @> lookups.
  • No DDL per content type. Schema changes migrate the stored data instead (§3).
  • Relations and media are stored as lists of ids whatever their cardinality (document ids of entries, numeric ids of posts, pages, users and attachments); components and dynamic zones as nested objects (dynamic zone items carry __component, component values an id).
  • Settings: the option headlessgo_settings (headless mode, CORS, public permissions, preview secret, page sizes, GraphQL switch, webhook attempts). API tokens: hg_api_tokens (SHA-256 only, can_upload). Webhooks: hg_webhooks, the delivery queue hg_webhook_queue, the attempt log hg_webhook_deliveries (last 200 per webhook).
  • Migration 0022_headlessgo_more.sql adds the schedule columns of hg_entries (publish_at, unpublish_at, schedule_error), the content history hg_entry_versions, hg_api_tokens.can_upload and hg_webhook_queue.
  • Migration 0024_headlessgo_review_lock.sql adds the edit locks (hg_entry_locks), the review columns of hg_entries (review_status, review_hash, review_by, review_note, review_at) and the history note.
  • Inverse relation fields (mappedBy) store nothing: their value is computed from the owning side.

2. Headless mode

Feature Status
While active the front end does not render: JSON 404 {"data":null,"error":{"status":404,"name":"NotFoundError",…}} ✓
Setting: plain-text 404, or a 302 to the front-end app's URL (optionally keeping path and query), or keep the site's front end ✓
wp-admin, wp-login, /wp-json (core REST and ?rest_route=), /wp-content/ (uploads, assets), /wp-includes/, wp-cron, robots.txt and the favicon keep working ✓
Logged-in users who can edit posts still see the front end (setting, on by default) so previews and theme work go on ✓
Runs in Server.Handler before the page cache (headlessServe); answers are no-store and noindex ✓

3. Content-Type Builder

Feature Status
Collection types (many entries), single types (one entry), components (category.name), dynamic zones ✓
Field types: text (short/long), rich text (blocks or Markdown), number (integer, big integer, decimal, float), boolean, date, date-time, time, email, password, enumeration, media (single/multiple, allowed types), relation, JSON, UID (derived from a text field), component (single/repeatable), dynamic zone ✓
Relations: one-to-one, one-to-many, many-to-one, many-to-many, to content types (self included) and to WordPress posts, pages and users ✓
Bidirectional relations: an owning field with inversedBy gets an inverse field (mappedBy) on the target type with the mirrored kind (one-to-one ↔ one-to-one, one-to-many ↔ many-to-one, many-to-many ↔ many-to-many); self relations too. The builder offers "Inverse field (optional)" on relations between content types. Both sides stay in step on every save: renaming either side renames the link, removing the inverse field clears inversedBy, removing (or retargeting) the owning field removes the inverse field, changing the kind changes the mirror. Export / import keeps them ✓
The inverse side stores nothing: its value is the owning entries pointing at the document (in the matching locale and status), so it can never disagree. It is populated, filterable and sortable like any relation, shown and editable in the Content Manager, and writable through the API (id, list, {connect, disconnect, set}, null clears); a write changes the owning entries' draft and published version (a link belongs to both documents). Cardinality is enforced (a single-valued inverse side takes one entry) ✓
Deleting a document (its last locale) removes it from every relation pointing at it: owning fields of every type, also inside components and dynamic zones, drafts and published versions ✓
One-to-one / one-to-many exclusivity (a target belongs to one entry) ✓
Options: required, unique, min/max (length, value or item count), default, private (never in the API), regex (text, UID, email) ✓
Type options: draft & publish, review before publishing, internationalization, preview URL template, description ✓
Builder page: type list, settings, field table with edit / delete / reorder, add-field panel with a type picker and per-type options ✓
Validation: kebab-case API ids, unique singular/plural ids, reserved names (id, documentId, locale, …), valid targets, no component cycles, no dynamic zone in components ✓
Schema changes migrate data: renamed fields (the builder sends renamedFrom) move their values; removed fields are dropped — in the type's entries, or inside every component value when a component changes (also nested and in dynamic zones); i18n on/off converts locales; draft & publish off publishes every draft ✓
Delete: a type (with its entries) or a component; refused while another schema uses or relates to it ✓
Export all schemas as JSON; import (file or paste): components first in dependency order, then types in two passes so they may relate to each other ✓
Changing a field (type, number format, rich-text format, single ↔ multiple media or relation, relation target, enumeration values, component, repeatable, dynamic zone components) converts the stored values of drafts and published versions, also inside components: text ↔ number ↔ boolean (yes/no, on/off, 1/0), dates ↔ date-times, text → UID (slugified), text → e-mail / enumeration (when valid, case-insensitive), blocks ↔ Markdown/text (plain text), anything → JSON, decimals → integers (rounded), multiple → single (first kept), repeatable → single component (first item). Values that cannot be converted are removed ✓
The builder lets an existing field change type, renames enumeration values changed on their line (enumRenames), shows a warning under the field when the change loses data and asks for confirmation on Save with the list of lossy changes ✓

4. Content Manager

Feature Status
Home with a card per type (entry counts, API route); side navigation ✓
Entries list: search (text fields and document id), status filter (draft / published / modified), locale filter, sortable columns, pagination ✓
Edit form generated from the schema for every field type: block editor for rich text (paragraph, headings, quote, code, lists, image; untouched blocks keep their inline formatting), media picker (WordPress media library), relation picker with search, nested components and dynamic zones with add / remove / reorder / collapse, JSON editor with validation, UID regenerate ✓
Validation per field options; a rejected save shows the errors next to the fields and keeps the input (passwords are never echoed back) ✓
Draft & publish: Save draft, Publish (validates required fields), Unpublish, Discard changes (back to the published version), status badges ✓
i18n: with Golylang active its languages are the locales; each document has one version per locale, linked by documentId; the edit screen lists the locales, opens a translation empty or filled from the current locale. With Golylang off there is one default locale (setting) ✓
Delete one locale or every locale ✓
Bulk actions in the list: publish, unpublish, delete the selected documents in the listed locale, or "in every locale"; failures (a required field empty) are reported per document ✓
Content history: every save, publish, unpublish, discard, restore, review step and scheduled (un)publication records the draft (last 50 per document version); the edit screen lists the latest, the History screen shows a version next to the current draft with changed fields marked, and restores it as the draft. Inverse relation fields are not part of a version; a link made or removed from the other side of a two-way relation is recorded instead (see below) ✓
Links across a two-way relation: saving an entry through its owning relation field adds a "Relations changed" version, with a note (Linked by Book "Dune" via books), to every entry that was linked or unlinked (their inverse field now lists something else); writing the inverse side adds one, with the new draft and a note (Linked Writer "Ada" via writer), to every owning entry whose data changed. Works from the admin, REST and GraphQL alike ✓
Restoring a version checks its values against the current schema first (types and formats, required, min / max, regex, enumerations, media and relation targets that still exist, unique fields). If something no longer fits, nothing is restored and the mismatches are listed; the History screen shows them before you click, and offers "Restore the fields that still fit": the mismatching fields keep their current values and the message names them. Password hashes are carried over untouched ✓
Scheduled publishing: "Publish on" / "Unpublish on" per document version (site time zone) in the edit screen, POST …/{documentId}/schedule in the API. The headlessgo_tick job of the site's job runner (every minute, rows claimed with FOR UPDATE SKIP LOCKED, safe across restarts and instances) publishes the draft as it is then, or unpublishes; a publication that fails validation is cleared and its reason shown on the edit screen; the list shows pending schedules ✓
Edit lock (WordPress post-lock style): opening an existing entry takes its lock (one per document version); the page's script renews it every 15 s (POST /wp-admin/headlessgo/lock, nonce-checked) and releases it when the page closes; a lock nobody renewed for 90 s is free. While someone else holds it the entry opens read-only with "X is currently editing this entry" and a Take over editing button; the server refuses every change from another user (save, publish, unpublish, discard, schedule, restore, delete), and a taken-over editor's open page is told by its next heartbeat and switches to read-only. A form also carries the version it was loaded from: a save on top of a newer one is refused ("changed by someone else"), also without a lock. The REST and GraphQL APIs are not locked (tokens have no user) ✓
Review flow: the type option Review before publishing (needs draft & publish). A draft is submitted for review; a user who can edit others' posts (editor and above) approves or rejects it (optional note). Publishing needs an approved draft, whatever the route: the form's Publish button (it saves the draft and publishes when that draft is approved, otherwise it says the draft was saved but not published), the REST publish route and ?status=published writes, GraphQL publish… / status: PUBLISHED, bulk publish, and scheduled publication (the schedule is cleared with the reason in the edit screen). Approval is bound to the exact draft: any later change (form, API, restore, relation link) makes it "not reviewed" again. Submit, approve and reject appear in the entry history with the reviewer's note. The APIs have no user, so they can neither submit nor approve; a type without the option is unchanged ✓

GET /upload/files/{id} ✓

Private fields: never returned, not filterable or sortable, but writable ✓
WordPress content: posts, pages and media are in the core REST API (/wp-json/wp/v2/posts, /pages, /media) and stay reachable in headless mode; HeadlessGo adds the missing menus: GET /wp/menus (menus and theme locations) and `GET /wp/menus/{id location
GET / lists the routes the caller may read ✓

6. Permissions and API tokens

Feature Status
Public role (no token): a matrix of type × find / findOne / create / update / delete under Settings. Default: nothing is public. Public callers never see drafts ✓
API tokens: read-only (find/findOne on every type), full access (everything, drafts included), custom (the same matrix per token, plus "may read drafts") ✓
Duration 7 / 30 / 90 days or unlimited; expired tokens get 401; last-used time (recorded at most once a minute); regenerate; delete ✓
Upload permission: full-access tokens always, custom tokens with "May upload media", read-only tokens and the public role never ✓
Only a SHA-256 of the token is stored; it is shown once (on the response page, never in a URL) with its last four characters in the list ✓
Authorization: Bearer <token>; a bad token is 401 UnauthorizedError, a missing permission 403 ForbiddenError ✓
Populated relations to a type the caller may not read are left out (not an error) ✓
Cookie / Application Password auth on this namespace ✗ tokens only (the admin uses its own screens)

7. CORS

  • Allow-list of origins (one per line, * for any) under Settings. Allowed origins get Access-Control-Allow-Origin (the origin itself) and Vary: Origin; preflight OPTIONS requests are answered with 204, the methods and the Authorization, Content-Type, Accept, X-Preview-Token headers, and a one-day Max-Age. Other origins get no CORS headers. Applies to the HeadlessGo namespace only. ✓

8. Webhooks

Feature Status
Events entry.create, entry.update, entry.publish, entry.unpublish, entry.delete, and schema.update (setting) ✓
Per webhook: name, URL, events, custom headers (reserved ones refused), signing secret, enabled ✓
Payload {event, createdAt, model, uid, entry} (public scalar attributes; private fields never sent) ✓
X-HeadlessGo-Signature: sha256=<hex HMAC-SHA256 of the body>, X-HeadlessGo-Event, X-HeadlessGo-Delivery ✓
Durable delivery queue (hg_webhook_queue): the first attempt starts at once in the background; a network error or a non-2xx answer is retried with an exponential backoff (10 s, 40 s, 160 s, 640 s…, at most 6 h) up to the "Attempts per delivery" setting (5 by default, 1–10), then the delivery is failed. Short backoffs are retried in-process; the headlessgo_tick job delivers whatever is due, so retries survive restarts (rows claimed with FOR UPDATE SKIP LOCKED; rows left running by a crashed instance return after 5 minutes). Finished rows are removed after a day ✓
The webhook screen lists waiting and failed deliveries (attempts, next attempt, last error) with "Retry now" ✓
Delivery log per webhook: date, event, attempt, status code, duration, the first 1 KB of the response or the error ✓
"Send test" (trigger-test, synchronous, result shown as a notice) ✓

9. Preview

  • Per type a preview URL template with {documentId}, {locale}, {status}, {secret}, {previewToken}, {uid}, {pluralApiId}, {singularApiId} and any scalar field ({slug}); values are URL-encoded. The edit screen shows Open preview. ✓
  • The preview secret (Settings, regenerable) is the {secret} front ends compare; it also keys the preview tokens. ✓
  • {previewToken}: a signed, short-lived token (lifetime setting, 60 min by default) that reads one document's draft: findOne of that document, or find restricted to it, with status=draft. Sent as Authorization: Bearer, X-Preview-Token or ?previewToken=. Rotating the secret revokes every preview token. ✓

10. GraphQL

  • POST|GET /wp-json/headlessgo/v1/graphql with {query, variables, operationName}. Root query fields: articles (camelCase plural id), article(documentId:), single types (homepage), articles_connection { nodes pageInfo { total page pageSize pageCount } }. Arguments filters (operators without $), sort, pagination, locale, status. Selections drive populate; aliases and __typename work. ✓
  • Mutations (POST only), with the REST permissions: createArticle(data:, locale:, status:), updateArticle(documentId:, data:, locale:, status:), deleteArticle(documentId:, locale:) → { documentId }, publishArticle / unpublishArticle(documentId:, locale:); single types updateHomepage, deleteHomepage, publishHomepage, unpublishHomepage (no documentId). Relations and media take ids, components and dynamic zones JSON. Validation errors come back as GraphQL errors. ✓
  • Named fragments (fragment Card on Article {…}, nested, cycles refused), inline fragments with or without a type condition (... on ComponentBlocksQuote), @include(if:) / @skip(if:), variables with default values, several operations selected by operationName. ✓
  • Introspection: __schema (types, query and mutation types, the two directives) and __type(name:) over a schema generated from the content model (object types per type and component, a union per dynamic zone, <Type>FiltersInput, <Type>Input, scalar filter inputs, PaginationArg, PublicationStatus, UploadFile, WpPost, WpUser, scalars JSON, Long, Date, DateTime, Time), enough for GraphiQL-type clients. ✓
  • Admin playground (HeadlessGo › GraphQL): a query and variables editor that runs as the logged-in administrator (POST /wp-admin/headlessgo/graphql, nonce-checked) or, with a pasted API token, against the public endpoint with that token's permissions; plus a reference of the root fields. ✓
  • Validation: a query is checked against the generated schema before it runs. An unknown field (also inside fragments and mutation results), an object field without a selection, a scalar with one (JSON scalars may have one), an unknown root argument or an unknown fragment type is a GraphQL validation error: HTTP 400, {"errors":[{"message":"Cannot query field \"titel\" on type \"Article\". Did you mean \"title\"?","extensions":{"code":"GRAPHQL_VALIDATION_FAILED"}}]}, no data, nothing executed (a mutation in the same request does not run). Every problem found is listed.
  • Subscriptions over server-sent events (the "distinct connections" mode of the graphql-sse protocol) on the same endpoint: send the subscription as a GET (?query=…, works with EventSource) or a POST (JSON body, works with fetch) with the usual Authorization: Bearer header and read the stream (Content-Type: text/event-stream). Root fields per content type: articleCreated, articleUpdated and articlePublished (only with draft & publish; the introspected Subscription type lists them), with arguments documentId (collection types) and locale; one root field per subscription. Each event runs the selection against the entry, so aliases, populate, fragments and variables work as in a query: event: next / data: {"data":{"articleCreated":{…}}}, : ping comments every 20 s, event: complete when the server ends the stream. Access follows REST: the type's findOne (single types: find) permission; a token that may read drafts gets Created and Updated with the draft values and Published with the published ones; every other caller gets Published only (for types without draft & publish also Created and Updated, published values). Validation errors, 403 and a full server (500 streams) answer as plain JSON before the stream starts. Limits: events are fanned out in the process that handled the write (a multi-instance setup needs the webhooks instead); unpublish and delete have no subscription (use the entry.unpublish / entry.delete webhooks); a stream is ended after 30 minutes (clients reconnect) and a subscriber that falls 256 events behind is dropped with an error event; no WebSocket transport (graphql-ws). The admin playground cannot show a stream and says so.
  • Not supported: custom directives; component inputs are JSON. The endpoint can be switched off under Settings.

11. Translations

  • The server-rendered screens go through the admin's i18n layer (internal/i18n, after rendering); the builder's field-type, relation and target labels are translated before they are sent as JSON; the strings the editor and builder scripts build in the browser are translated by wpgo-l10n.js (admin/assets/headlessgo/*.js is one of its sources). User content is marked translate="no".
  • Turkish (web/languages/wpgo-tr_TR.json) covers HeadlessGo's admin screens. Other languages: the strings shared with WordPress core come from its language packs; HeadlessGo's own strings stay English.

12. Not built / limits

  • Relation ordering beyond the stored order (the owning side's order; the inverse side lists owners by creation).
  • History does not record link changes made by a schema conversion or by deleting a related document (the deleted document's links disappear from the owners' drafts without a version), and a link that moves from one inverse-side entry to another through the inverse field is recorded on the owning entry and the new target, not on the entry that lost it.
  • Edit locks and the review flow belong to the admin: the REST and GraphQL APIs are not locked and cannot submit, approve or reject (they are refused when publishing an unapproved draft). The review capability is "may edit others' posts" and is not configurable per type; a reviewer may approve a draft they submitted themselves.
  • GraphQL: custom directives; subscriptions are server-sent events from one process (see §10); component inputs are JSON.
  • Translations of HeadlessGo's own admin strings exist only in Turkish.
